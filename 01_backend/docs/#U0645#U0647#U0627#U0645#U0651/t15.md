# أميال باي — مهمة تدقيق وتوحيد وإغلاق قطاع التحقق والهوية KYC

هذه مهمة **تدقيق وإصلاح وتوحيد وإعادة تصميم كاملة في جولة واحدة متصلة** للشاشة:

`لوحة الإدارة → العملاء → لوحة التحقق (الحسابات الجديدة)`

والنظام الموازي الموجود حاليًا:

`لوحة الإدارة → مراجعة مستندات الهوية KYC`

وكل ما يرتبط بهما من:

- تسجيل العميل/التاجر/الوكيل
- حالة الحساب `is_kyc_verified`
- مستويات KYC
- `KycDocument`
- الملفات المشفرة
- OCR
- MerchantProfile
- Zone assignment
- Approval / Maker–Checker
- RBAC
- PII access
- Notifications
- تطبيق Flutter Account Review
- الحظر/فك الحظر
- Audit
- Fraud/AML context
- mobile
- production truth

لا تعد بعد كل Bug. نفّذ:

`Audit → Truth Mapping → Duplicate-System Discovery → State-Machine Truth → Document Truth → Role-Specific Requirements → RBAC → PII → Review Workflow → Account Activation → Zone → Merchant/Agent Activation → Security → Concurrency → Fix → Unify → Redesign → E2E → Regression → Production Verification → Final Verdict`

لا تعتبر القطاع مكتملًا لأن «لوحة التحقق» تقول صفر حسابات، أو لأن زر «اعتماد» يغيّر `is_kyc_verified`.

المطلوب إنهاء **قطاع Verification/KYC بالكامل** وليس هذه الصفحة وحدها.

## المسار القديم / Account-level
`/admin/amial/hub/verification`

- `users.is_kyc_verified`

- حظر/فك حظر من نفس الشاشة

`/admin/amial/kyc`

يعتمد على:
- `kyc_documents`
- ملفات مشفرة
- `KycDocumentService`
- مراجعة كل مستند
- OCR
- إقرار الحقول
- سبب رفض
- PII access audit
- document expiry
- completeness

لا تبدأ تجميل الصفحة قبل حسم:

`Which system is authoritative?`

أريد في النهاية:

`authoritative KYC review systems = 1`

# 3. أخطر ثغرة معمارية: لوحة التحقق القديمة تتجاوز KycDocumentService

`POST /hub/users/{id}/kyc {status: 1}`

`users.is_kyc_verified = 1`

هذا يمكن أن يعتمد حسابًا دون المرور على:

- اكتمال المستندات
- حالة كل KycDocument
- انتهاء الوثيقة
- OCR findings
- reviewer-confirmed fields
- rejection history
- four-eyes document rule

أثبت عمليًا:

هل يمكن إنشاء حساب pending، بلا `kyc_documents` مكتملة، ثم اعتماده من Hub؟

إذا نعم:
هذه **KYC bypass حرجة**.

أريد:

`account verification bypassing document truth = 0`

- هل متصفح الأدمن يخزنها؟
- هل لها expiry/review metadata؟

قرر Migration:

`legacy identity images → KycDocument records`

أو Read-only legacy compatibility.

لا تسمح أن تبقى:

`public legacy docs + encrypted KYC docs`

كمصدرين حيّين.

# 6. افصل Document Approval عن Account Approval

هذه نقطتان مختلفتان:

`Document approved`

لا تعني:

`Account approved`

وهي فلسفة `KycDocumentService` الحالية أصلًا.

حافظ عليها.

لكن أغلق الحلقة:

`all required documents approved`
+
`required fields confirmed`
+
`role-specific requirements complete`
+
`risk rules acceptable`
+
`reviewer decision`
=
`account eligible for activation`

ثم Account Approval منفصل وواضح.

`0 / 1 / 2`

- `draft`

- `pending_review`
- `needs_information`
- `under_manual_review`
- `approved`
- `rejected`
- `suspended`
- `expired`
- `reverification_required`

إذا `is_kyc_verified` يجب أن يبقى للتوافق:
اجعله Projection من state authoritative، لا المصدر الوحيد.

أريد:

`ambiguous KYC states = 0`

# 8. رفض الحساب ليس نفس رفض مستند

مثال:
صورة الخلفية رديئة.

لا ينبغي أن يكون الحساب كله `rejected` نهائيًا إذا المطلوب فقط إعادة رفع مستند.

أضف:

`needs_information`

و:

`document_reupload_required`

بدل إسقاط الحساب كله إلى rejected عند مشكلة قابلة للإصلاح.

# 9. سبب الرفض إلزامي في كل مستوى

النظام الأحدث يرفض Document فقط مع Reason.

الشاشة القديمة ترفض الحساب بلا Reason.

هذا غير مقبول.

أي رفض Account يحتاج:

- reason_code
- reason_note
- affected requirements
- what customer can fix
- whether reapply allowed
- reviewer
- timestamp

ويصل السبب المناسب للعميل.

# 10. Notification الحالية للرفض عامة جدًا

لا تكشف Fraud detection internals الحساسة.

أنشئ:
`customer_safe_reason`
و:
`internal_review_reason`

# 12. Role-specific verification

الشاشة تجمع:

- عميل
- تاجر
- وكيل

لكن requirements ليست واحدة.

أنشئ Registry:

`VerificationRequirementsRegistry`

لكل Role:

## Customer
- identity front
- identity back
- selfie
- address proof حسب tier/policy

## Merchant

- trade license إن كان مطلوبًا
- store/business details
- business type
- merchant record
- ownership/authorized representative
- branch/site info حسب السياسة

## Agent
بالإضافة إلى الهوية:
- agency/exchange company requirements
- branch/cash node data
- operational eligibility
- zone/location agreement

لا تخترع مستندات قانونية غير معتمدة؛ استخرج المطلوب من المشروع والسياسة الحالية.

# 19. Audit durability

# 24. أكبر bypass أمني خارج KYC: حظر/فك الحظر

هذا حرج.

أريد:

`unfreeze approval bypass paths = 0`

PII / الهواتف / الهوية / OCR.

الحظر، فك الحظر، Four Eyes.
