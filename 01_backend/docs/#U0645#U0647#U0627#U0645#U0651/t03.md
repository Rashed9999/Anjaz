# أميال باي — مهمة التدقيق والإصلاح الشامل لشاشة **مركز العملاء**
## تسليم واحد فقط — كل التبويبات والإجراءات والبيانات والصلاحيات والاختبارات في ملف واحد

> **النطاق:** هذه المهمة تخص شاشة واحدة فقط في لوحة الإدارة:
>
> `العملاء → ملف العميل (الويب) → مركز العملاء`
>
> كل الصور المرسلة هي تبويبات داخل نفس الشاشة، وليست شاشات منفصلة.

---

# 0. قاعدة التنفيذ

نفّذ هذه المهمة كقطاع واحد:

`Images Audit → Repository Truth → Route/RBAC Truth → Data Truth → Financial Truth → Security Truth → KYC Truth → Risk Truth → Fix → Redesign → Wire → Attack Tests → Regression → Browser Probe → Production Verification → Final Verdict`

لا تعد بعد كل Bug.

لا تعتبر الشاشة مغلقة لأن:
- الـHTML يفتح،
- التبويب يعيد 200،
- جدولًا يظهر،
- أو الاختبارات الحالية خضراء.

**كل قيمة يجب أن يكون لها مصدر، وكل زر يجب أن ينفّذ الفعل الصحيح، وكل صلاحية يجب أن تكون على الـBackend، وكل إجراء حساس يجب أن يترك أثرًا دائمًا ومفهومًا.**

والـUI نفسها تبني التبويبات من الصلاحيات المسموح بها، لا تعرض Tab ثم تنتظر 403.

## 2.4 خطأ KYC معروف ما زال موجودًا داخل CustomerCenterService

`CustomerStatusResolver` تم تصميمه عمدًا ليعتبر KYC موثقًا فقط عندما:

`(int) is_kyc_verified === 1`

لأن القيمة القديمة/الافتراضية قد تكون `3`، والكود المالي يعتبر أي قيمة غير 1 غير موثقة.

لكن `CustomerCenterService::overview()` و`kyc()` ما زالا يستخدمان:

`(bool) ($customer->is_kyc_verified ?? false)`

أي أن `3` تصبح `true`.

هذا يُنشئ تناقضًا داخل نفس الشاشة:
- رأس الحالة قد يقول KYC pending
- Card/Tab قد تقول verified

أصلحه في **كل موضع**.

لا تسمح بأي cast bool لهذا الحقل.

أريد:
`KYC verified semantics = strict authoritative state`

# 3. مشكلة الرصيد 18,000 مقابل «لا عمليات»

هذه أهم نقطة Data/Financial Truth ظاهرة في الصور.

المحفظة:
`18,000 YER`

العمليات:
`لا عمليات`

`CustomerCenterService::wallets()` يقرأ الرصيد من `EMoney.current_balance`.

`transactions()` يقرأ من جدول `transactions` ويشمل:
- user_id
- from_user_id
- to_user_id

إذن يجب إثبات مصدر الـ18,000.

لا تفترض أن أحدهما خطأ.

افحص:

1. هل الـ18,000 جاءت من Seed/Legacy migration؟
2. هل جاءت من Admin top-up لا يكتب في transactions؟
3. هل جاءت من Ledger lines لا توجد لها Transaction legacy row؟
4. هل Query operations يفوّت أنواعًا من الحركة؟
5. هل transaction table الحالي ليس Truth الكامل؟
6. هل balance current field diverged عن ledger-derived balance؟

المطلوب إنشاء:

`CustomerFinancialTraceService`

أو استخدام Financial Truth Service الحالية إن وجدت.

يجب أن يرجع على الأقل:

- stored wallet balance
- held
- pending
- available
- ledger-derived balance
- reconciliation status
- unexplained variance
- first money source
- latest money movement

إذا الرصيد موجود بلا حركة قابلة للتفسير:
لا تعرض الشاشة أخضر.

اعرض:

`⚠ رصيد غير مفسّر بالكامل`

مع drill-down.

**Definition:**  
`wallet balance with no explainable financial origin = 0`

# 13. أخطر bypass: unfreeze مباشر من Customer Center

`CustomerActionService::unfreeze` ينفذ:

`setFrozen(false)`

مباشرة.

بينما مركز الدعم الموجود في المشروع لديه Approval/Maker–Checker لفك التجميد.

إذن يوجد بابان لنفس الفعل:
- مسار يخضع للموافقة
- مسار مركز العملاء يرفعه فورًا

هذا **Four-Eyes bypass**.

الحل:
كل Unfreeze في المشروع يمر من:

`AccountRestrictionService / ApprovalService`

واحد.

لا يوجد Direct setFrozen(false) من هذه الشاشة.

**Definition:**  
`unfreeze approval bypass paths = 0`

# 26. Race عند تبديل العميل أو التبويب بسرعة

الحالي لا يستخدم AbortController أو request sequence.

سيناريو:
1. افتح العميل A / risk
2. مباشرة افتح العميل B
3. رد A البطيء يصل بعد B
4. قد يُرسم داخل UI الحالية

أضف:
- request token
