# أميال باي — مهمة تدقيق وإغلاق قطاع استعادة الحساب وتغيير رقم الهاتف

هذه مهمة **تدقيق أمني وتشغيلي وإعادة تصميم وإغلاق كاملة في جولة واحدة متصلة** للشاشة:

`لوحة الإدارة → العملاء → طلبات استعادة الحسابات`

وكل ما خلفها من:

- `AccountRecoveryService`
- `AccountRecoveryRequest`
- Admin `AccountRecoveryController`
- User API `AccountRecoveryController`
- Flutter `AccountRecoveryScreen`
- مسار فقدان الهاتف
- تغيير رقم الهاتف
- OTP
- PIN
- مستندات إثبات الهوية
- Security Hold
- Token/Session revocation
- FCM/device state
- Risk scoring
- Maker–Checker
- KYC
- PII
- Audit
- Notifications
- scheduled application after hold
- phone uniqueness
- RBAC
- concurrency
- recovery history
- mobile
- production truth

لا تعد بعد كل Bug. نفّذ:

`Audit → Threat Model → Recovery Truth Map → Authentication Truth → Ownership Proof → Document Truth → Risk Truth → Approval Truth → Hold Truth → Final-Apply Truth → Sessions/Devices → RBAC → PII → Concurrency → Fix → Redesign → Wire → Attack Tests → E2E → Regression → Production Verification → Final Verdict`

لا تعتبر القطاع مكتملًا لأن الطلب يظهر في قائمة الإدارة أو لأن زر «اعتماد» يضع `security_hold_until`.

الهدف:

`ACCOUNT RECOVERY MUST NEVER BECOME AN ACCOUNT TAKEOVER PATH`

---

## 1. ابدأ بخريطة الحقيقة كاملة

ارسم السيناريوهين:

### A — المستخدم يملك الرقم القديم

`Authenticated account`
→ `new phone`
→ `OTP old`
→ `OTP new`
→ `PIN`
→ `risk decision`
→ `security hold`
→ `revoke sessions/devices`
→ `final phone change`
→ `new login identity`
→ `notifications/audit`

### B — المستخدم فقد الرقم القديم

`Cannot rely on old phone`
→ `find account`
→ `prove identity`
→ `prove ownership of new phone`
→ `documents/KYC`
→ `risk`
→ `review`
→ `maker/checker if required`
→ `security hold`
→ `out-of-band alerts`
→ `final phone change`
→ `sessions/devices reset`
→ `new authentication`

أثبت كل سهم بالشيفرة الفعلية.

## 2. أخطر سؤال: كيف يبدأ Lost Phone Recovery إذا كان المستخدم لا يستطيع الدخول؟

مسارات Recovery الحالية تقع داخل:

`auth:api`

والـController يستعمل:

`$request->user()`

لكن السيناريو اسمه:

`phone_change_lost_phone`

أي المستخدم قد يكون فقد الرقم/الجهاز الذي يعتمد عليه للدخول.

أثبت UX الحقيقي:

- هل يستطيع العميل الوصول إلى Lost Phone Recovery من شاشة تسجيل الدخول؟
- هل يحتاج Token سابقًا؟
- ماذا لو لا يوجد جهاز آخر مسجل؟
- ماذا لو SIM ضاعت والهاتف أيضًا ضاع؟

إذا Lost Phone Recovery يحتاج Session مصادقًا سلفًا، فهو ليس Recovery كاملًا بل **Authenticated phone-change escalation**.

إما:
- صمّم Public Recovery Bootstrap آمنًا جدًا،
- أو صحح الاسم/النطاق.

شرط:

`lost-phone users requiring impossible prior authentication = 0`

إذا لا:

`lost-phone approval without verified new-phone ownership = 0`

## 7. AdminApprove لا يعتمد على status فقط

لا يكفي:

`status === pending_review`

قبل الاعتماد يجب أن توجد Preconditions مركزية:

- request not expired
- user exists
- user eligible
- new phone normalized
- new phone unique now
- new phone ownership verified
- identity evidence verified
- required KYC consistency checked
- risk calculated
- no conflicting active recovery
- no critical fraud/security block
- no protected role rule violated
- no stale version
- reviewer authorized
- maker != checker where required

## 8. Expired request approval

`isExpired()`

اختبار:
- request expires
- scheduler لم يغير status
- Admin يفتح URL قديم
- Approve

`410 RECOVERY_EXPIRED`

شرط:

`expired recoveries approvable = 0`

## 9. Expiration State Truth

## 10. Security Hold Timeline مستقل عن Request TTL

Lost-phone request expires بعد 7 أيام من الإنشاء.

Admin approval يضع hold سبعة أيام **من وقت الموافقة**.

إذا وافق Admin في اليوم السادس:
- request expires في اليوم السابع
- hold ينتهي في اليوم الثالث عشر

لا تستخدم نفس `expires_at` لتمثيل lifecycle بعد approval.

أضف:
- `request_expires_at`
- `hold_started_at`
- `hold_until`
- `applied_at`

واضحة.

## 11. State Machine الحالية ناقصة

الحالة `approved` تعني حاليًا:
**الموافقة تمت والـhold فعال**.

لكن ماذا بعد تطبيق الرقم؟

لا يوجد State واضح مثل:

- `pending_otp`
- `pending_identity`
- `pending_review`
- `approved_hold`
- `cancelled_during_hold`
- `ready_to_apply`
- `applying`
- `applied`
- `rejected`
- `expired`
- `failed_apply`

أريد State Machine رسمية.

شرط:

`approved-but-not-applied ambiguity = 0`

## 12. أثبت أن التغيير «التلقائي بعد الـHold» يحدث فعلًا

الواجهة تقول:

**سيتم تغيير الهاتف تلقائيًا بعد انتهاء مهلة الأمان.**

لكن ابحث repository-wide عن المستهلك الفعلي لـ:

`AccountRecoveryService::applyApprovedChange()`

أريد:

`Scheduler/Job/Worker → applyApprovedChange`

مع اختبار production.

إذا method موجودة فقط في Service/Tests/Docs ولا يوجد Job أو Schedule يستدعيها:
فالواجهة **تعد بشيء لا يحدث تلقائيًا**.

هذه P0.

شرط:

`approved recoveries with no automatic finalizer = 0`

## 13. Recovery Finalizer

أنشئ Job/Scheduler idempotent:

`FinalizeApprovedRecoveryJob`

يفحص:
- approved_hold
- hold elapsed
- request not revoked/cancelled
- new phone still unique
- user unchanged in incompatible way
- security/risk not escalated during hold
- version matches

ثم يطبق atomically.

## 14. Finalizer must be idempotent

تشغيله مرتين:
لا يغير الهاتف مرتين
ولا يسجل events مكررة
ولا يعيد notifications
ولا يكسر phone indexes.
