## المشكلة 1: انقطاع النت → خصم مزدوج

### النتيجة: **محلولة بالفعل** ✅ (تحقّقنا، لم نكرّر)

عند الفحص، اكتُشف أن النظام **مُحصَّن بالكامل** ضد هذه المشكلة عبر بنية
idempotency موجودة من إصدارات سابقة:

```
الطبقات الموجودة:
  1. Flutter: IdempotencyKeyGenerator يولّد مفتاحاً فريداً لكل عملية
  2. Backend: EnforceIdempotency middleware على كل مسار مالي
  3. Service: IdempotencyService (begin/complete/fail)
  4. DB: جدول idempotency_keys
```

### كيف يحمي من انقطاع النت

```
المستخدم يضغط "إرسال 10,000"
  → Flutter يولّد Idempotency-Key فريد ويرسله في الـ header
  → الخادم ينفّذ بنجاح، يحفظ النتيجة بالمفتاح
  → ❌ النت ينقطع، الرد لا يصل
  → المستخدم يعيد الضغط (نفس المفتاح)
  → ✅ الخادم يكتشف التكرار → يُرجع النتيجة المحفوظة
     (X-Idempotent-Replay: 1) دون خصم ثانٍ
```

**النتيجة:** لا خصم مزدوج مهما تكرر الإرسال. هذا بالضبط ما تحتاجه شبكة اليمن.

### ملاحظة صادقة

في فحصي الأول ظننت وجود ثغرة (لأن `idempotency_key` في جدول transactions
كان index عادياً لا unique). لكن **الحماية الفعلية في طبقة الـ middleware
+ service**، وهي تعمل قبل الوصول للجدول. تحققت من الكود فعلياً قبل التأكيد —
التزاماً بقاعدة "لا ادعاء دون دليل".

## المشكلة 2: تحويل بالغلط → الحل الجديد ⭐

### المشكلة الحقيقية

التحويل كان يأخذ رقم الهاتف ويُرسل **فوراً** دون تأكيد اسم المستلم.
خطأ رقم واحد = المال لشخص آخر، بلا رجعة (التحويل نهائي محاسبياً).

### الحل: RecipientVerificationService

نمط قياسي في تطبيقات الدفع — **تأكيد المستلم قبل الإرسال**:

```
1. العميل يدخل رقم الهاتف
   → POST /amial/transfer/verify-recipient
2. النظام يُرجع:
   - الاسم المُقنّع: "أحمد م** ع**"  (للتأكيد البصري)
   - الرقم المُقنّع: "777****56"
   - هل تاجر؟
   - verification_token (صالح 5 دقائق)
3. العميل يرى الاسم → يؤكد بصرياً أنه الصحيح
4. التحويل لا يُقبل إلا بـ token صالح للمستلم نفسه
```

### لماذا الاسم مُقنّع؟

حماية الخصوصية: لا نكشف الاسم الكامل لأي شخص يدخل رقماً عشوائياً
(يمنع حصاد البيانات/enumeration)، لكن يكفي ليتعرّف المرسل على مستلمه.

### حماية إضافية

| الحماية | الآلية |
|---|---|
| token single-use | يُستهلك بعد استخدام واحد |
| token مربوط بالمرسل+المستلم | لا يُعاد استخدامه لتحويل آخر |
| انتهاء صلاحية 5 دقائق | لا تأكيد قديم |
| فحص المنطقة | المستلم يجب أن يكون SOUTH |
| منع التحويل للنفس | فحص senderId |

## التكامل المطلوب (مهم)

### Backend — ربط الـ token بـ send_money

في `customer_send_money_transaction`، أضف فحص الـ token (اختياري حالياً،
يُفعّل عند جاهزية Flutter):

```php
// في بداية sendMoney controller، قبل التنفيذ:
if ($request->filled('verification_token')) {
    app(\App\Services\RecipientVerificationService::class)
        ->assertValidToken($sender->id, $request->verification_token, $recipientId);
}
```

### Flutter — تدفق التأكيد

```dart
// 1. قبل شاشة المبلغ، تحقق من المستلم
final result = await repo.verifyRecipient(phone);
// 2. اعرض الاسم المُقنّع للمستخدم
showDialog("هل تريد التحويل إلى: ${result['masked_name']}؟");
// 3. عند التأكيد، أرسل verification_token مع التحويل
await repo.sendMoney(..., verificationToken: result['verification_token']);
```

## الإجابة الكاملة على سؤالك

### "هل المشروع مصمم للتعامل مع هذه المشاكل؟"

| المشكلة | الإجابة الصادقة |
|---|---|
| **انقطاع النت → خصم مزدوج** | ✅ **نعم، محمي بالكامل** (idempotency من 3 طبقات) |
| **تحويل بالغلط** | 🔧 **لم يكن محمياً، أصلحناه الآن** (تأكيد المستلم) |

### الدرس المهم

سؤالك كشف:
1. **نقطة قوة** لم تكن تعرفها (الـ idempotency محكم)
2. **فجوة حقيقية** (لا تأكيد مستلم) أصلحناها

هذا بالضبط سبب أهمية **اختبار النظام بأسئلة من الواقع**. المطور يبني الميزات،
لكن المستخدم الذي يعرف بيئته (ضعف النت، أخطاء الأرقام) يكشف ما يحتاج فعلاً.

## ملاحظة عن "التحويل بالغلط" — حدود الحل

التأكيد البصري **يقلّل** الأخطاء بشكل كبير، لكنه **لا يلغيها 100%**:
- لو المستخدم لم يقرأ الاسم وضغط "تأكيد" بسرعة → قد يخطئ

### حلول تكميلية مستقبلية (اختيارية)

| الحل | الفائدة |
|---|---|
| **نافذة إلغاء قصيرة** (30 ثانية بعد التحويل) | تراجع فوري |
| **تأخير التحويلات الكبيرة** (للمستلمين الجدد) | فرصة للمراجعة |
| **قائمة المستلمين المتكررين** (favorites) | تقليل إدخال الأرقام يدوياً |
| **تأكيد PIN للمبالغ الكبيرة** | طبقة إضافية |

الأول (نافذة الإلغاء) هو الأقوى لـ "التحويل بالغلط" — لكنه يحتاج تصميماً
دقيقاً (ماذا لو المستلم سحب المال فوراً؟). يمكن بناؤه لاحقاً كـ
`AMIAL-TRANSFER-COOLDOWN-001` إن أردت.
