# أميال باي — مهمة شاملة لإغلاق قطاع هوية موظفي المنصة والأدوار والصلاحيات والمصادقة الثنائية
## Platform Workforce IAM + RBAC + MFA + Session Security

> هذه المهمة تخص شاشتين مترابطتين ضمن قطاع أمني واحد:
> 1. أدوار الموظفين
> 2. المصادقة الثنائية
>
> لا يجوز إصلاح واحدة وترك الأخرى؛ لأن منح الدور، تسجيل الدخول، MFA، الجلسة، وتعطيل الموظف كلها أجزاء من نفس دورة الوصول إلى أميال باي.

---

# 1) القاعدة المعمارية

الهدف النهائي:

`Identity`
→ `Account Status`
→ `Portal Classification`
→ `MFA`
→ `Role`
→ `Permissions`
→ `Session`
→ `Authorized Workspace`
→ `Audit`

ويجب الفصل بين:
- Platform Admin Portal
- Platform Staff Portal

بحيث لا يمر موظف الدعم/المالية/المخاطر/الامتثال من نفس بوابة مدير المنصة ثم نكتفي بإخفاء القائمة.

---

# 2) نظام الأدوار الحالي

احتفظ بالبنية الحالية المبنية على:
- roles
- permissions
- role_permissions
- admin_user_roles

والأدوار الحالية تشمل:
- platform_admin
- platform_supervisor
- platform_support
- platform_maintenance
- platform_finance
- platform_risk
- platform_compliance

لا تعِد بناء RBAC من الصفر.

---

# 3) مشكلة إنشاء موظف بلا دور

مسار إنشاء الموظف الحالي يسمح بأن تكون:
`role_ids = []`

ثم ينشئ الحساب:
- type = ADMIN_TYPE
- is_active = 1
- is_phone_verified = 1

المطلوب:

`new active platform employee with zero effective roles = forbidden`

إذا لم يكتمل الإسناد:
- status = pending_provisioning
- لا Login
- لا Session
- لا Workspace

---

# 4) لا تعتبر الهاتف موثقًا لأن المدير كتبه

لا تستخدم:
`is_phone_verified = 1`

لمجرد أن المدير أدخل الرقم.

التدفق الأفضل:
- المدير ينشئ الموظف
- status = invited / pending_activation
- الموظف يثبت ملكية الهاتف
- يضع كلمة مروره بنفسه
- يسجل MFA
- يصبح active

لا تجعل المدير يعرف كلمة المرور الدائمة للموظف.

---

# 5) منع Role Injection

التحقق من:
`exists:roles,id`

غير كافٍ.

يجب تقييد role_ids إلى:
- merchant_user_id IS NULL
- code LIKE platform_%

حتى لا يستطيع POST مزور إسناد Role لا يخص موظفي المنصة.

---

# 6) platform_admin ليس Checkbox عاديًا

عامل:
`platform_admin`

كدور حساس:

- recent authentication
- MFA
- reason
- critical audit
- approval إضافي عند الحاجة

ويفضل أن يكون Exclusive عن الأدوار التشغيلية الدقيقة أو يخضع Conflict Policy واضحة.

---

# 7) Separation of Duties

أنشئ Role Conflict Matrix.

راجع تعارضات مثل:
- Maker + Checker
- Money mover + Reconciler
- KYC submitter + KYC approver
- Treasury maker + Treasury checker
- Role administrator + own approval

أي تعارض:
- يمنع Server-side
أو
- يتطلب Exception موثقة

---

# 9) فحص التكرار الظاهر

الصورة الحالية تعرض صفين متطابقين تقريبًا باسم مدير النظام وبنفس الهاتف/البريد الظاهر.

نفذ Identity Integrity Check:

- duplicate normalized phone
- duplicate email
- duplicate platform identity
- orphan role assignments
- stale duplicate admin records

ولا تفترض أنها مشكلة UI قبل الفحص.

الحكم:
`duplicate platform identity UNKNOWN = 0`

---

# 10) Employee Lifecycle

الحالات المقترحة:
- invited
- pending_activation
- active
- suspended
- locked_security
- on_leave
- terminated

عند Suspend/Terminate:
- deny login
- revoke sessions
- revoke remember tokens
- revoke trusted devices
- invalidate pending MFA challenge
- revoke API tokens إن وجدت
- preserve audit/history

لا تحذف الموظف لأنه جزء من التاريخ.

---

# 11) Role History

لا يكفي حذف أدوار الموظف وإضافة الجديدة فقط.

احفظ تاريخ:
- role
- granted_at
- granted_by
- revoked_at
- revoked_by
- reason

حتى نعرف من كان يملك أي صلاحية وقت تنفيذ عملية قديمة.

---

# 12) Role Change يجب أن يعمل فورًا

عند تغيير الأدوار:
- recompute permissions
- invalidate authorization cache
- revoke/refresh sessions حسب السياسة
- update workspace
- audit

لا تبقى جلسة قديمة بصلاحيات سُحبت.

---

# 13) حماية آخر مدير

احتفظ بقاعدة:
- لا يمكن سحب Admin Role من آخر مدير صالح
- لا يمكن ترك المنصة بلا مدير قابل للدخول

لكن احسب فقط المدير:
- active
- غير terminated
- قابل للدخول
- يملك MFA إذا السياسة تتطلبه

---

# 14) 2FA الحالي — احتفظ بأساسه

الأساس الحالي جيد ويشمل:
- TOTP RFC6238
- 6 digits
- 30s
- ±1 time window
- encrypted secret
- recovery codes
- single-use recovery
- replay protection
- rate limiting
- challenge قبل فتح جلسة Admin
- session regeneration

لا تعِد بناءه بلا سبب.

---

# 15) المشكلة الأساسية: 2FA اختياري

الدخول يفرض العامل الثاني فقط إذا كان المستخدم قد فعّله أصلًا.

المطلوب:

`MFA policy determines access`

وليس:
`user preference determines access`

الحد الأدنى الإلزامي:
- platform_admin
- platform_finance
- platform_risk
- platform_compliance
- أي دور يحرك المال
- أي دور يغير الصلاحيات
- أي دور يعيد ضبط MFA

والأفضل:
`all platform employees = MFA mandatory`

---

# 16) Enrollment Gate

إذا نجحت كلمة المرور لكن MFA مطلوب ولم يُفعّل:

`password verified`
→ `MFA enrollment gate`
→ `QR/manual secret`
→ `confirm code`
→ `recovery codes acknowledged`
→ `session issued`

لا يدخل Dashboard قبل الإكمال.

---

# 17) تعطيل MFA

إذا الدور يفرض MFA:
`disable = forbidden`

أو يحتاج Workflow أمني:
- recent auth
- reason
- independent approval
- session revocation
- audit

---

# 18) Recovery Codes

الأفضل:
- display once
- store hashes
- single-use
- no recoverable plaintext after setup

ولا تحفظها بشكل يمكن فك تشفيره لاحقًا إلا إذا كان هناك Risk Acceptance صريح.

---

# 19) Rate Limiting موحد

وحّد السياسة بين:
- setup confirm
- login challenge
- recovery
- disable
- regenerate

ولا تترك 5 دقائق في طبقة و15 دقيقة في طبقة أخرى برسائل مختلفة.

---

# 45) توجيه حازم

لا تحوّل المهمة إلى تجميل Checkboxes وQR.

هذه الشاشة تتحكم بمن يستطيع:
- رؤية أموال الناس
- تحريك المال
- تجميد الحسابات
- قبول KYC
- تغيير الإعدادات
- منح الصلاحيات

المطلوب:

`Verified Identity`
→ `Correct Role`
→ `Mandatory MFA`
→ `Least Privilege`
→ `Session Control`
→ `Immutable Audit`

وأي فجوة في هذه السلسلة تعني أن القطاع لم يُغلق.
