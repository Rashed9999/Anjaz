# أميال باي — مهمة تدقيق وتوحيد وإغلاق مركز الإعدادات والسياسات التشغيلية

هذه مهمة **تدقيق أمني وتشغيلي ومالي وإعادة تصميم وتوحيد كاملة في جولة واحدة متصلة** للشاشة:

`لوحة الإدارة → الإعدادات والتشغيل → إعدادات سريعة (تشغيل/إيقاف)`

والشاشة الحالية التي تعرض ثلاثة مفاتيح:

- التحقق بالهاتف `phone_verification`
- مكافآت الإحالة `referral_earning_status`
- وضع الصيانة العام `maintenance_mode`

لكن المطلوب لا يقتصر على هذه الثلاثة؛ يجب فحص **كل مصدر ومستهلك ومحرر فعلي** لهذه السياسات في المشروع، بما في ذلك:

- `business_settings`
- `Setting / addon_settings / ops_config`
- `AdminHubController::settings / settingsToggle`
- `BusinessSettingsController`
- `AdminOpsController`
- `AmialMaintenanceMode`
- `FeatureFlagService`
- `RequireFeatureEnabled`
- `/admin/maintenance`
- `ConfigController`
- `RegisterController`
- Customer/Agent registration and OTP flows
- `OtpPolicy`
- `phone_verifications`
- referral payment logic
- `Helpers::add_refer_commission`
- ledger / MoneyService / transaction truth
- app configuration
- cache/config propagation
- RBAC
- Audit
- Maker–Checker
- production runtime
- mobile admin UI
- tests

لا تعد بعد كل Bug. نفّذ:

`Audit → Setting Registry → Source-of-Truth Mapping → Consumer Mapping → Duplicate Editors → Dead Flags → Security Impact → Financial Impact → Maintenance Truth → Referral Truth → OTP Truth → RBAC → Audit → Concurrency → Fix → Unify → Redesign → E2E → Attack Tests → Regression → Production Verification → Final Verdict`

لا تعتبر الشاشة مكتملة لأن الـSwitch تغير في قاعدة البيانات.

المعيار هو:

`ADMIN CONTROL CHANGED → AUTHORITATIVE RUNTIME BEHAVIOR CHANGED EXACTLY AS ADVERTISED`

# 2. أهم اكتشاف يجب حسمه: ثلاثة مفاتيح لا تعني ثلاثة حقائق صحيحة

الشاشة الحالية تكتب الثلاثة في:

`business_settings`

لكن المشروع لا يقرأ كل واحد منها من هذا المصدر.

أثبت لكل مفتاح:

`write source == runtime read source`

شرط:

`settings whose admin write source differs from runtime read source = 0`

---

# 3. maintenance_mode في هذه الشاشة يبدو مفتاحًا ميتًا/مضللًا

الشاشة الحالية تكتب:

`business_settings.key = maintenance_mode`

لكن `AmialMaintenanceMode` الفعلي يقرأ:

`config_settings('maintenance_mode', 'ops_config')`

أي من منظومة `Setting/addon_settings` وليس `business_settings`.

وهناك `AdminOpsController::setMaintenance()` يكتب إلى:

`maintenance_mode + ops_config`

إذن يوجد محرران/مصدران لنفس المعنى الظاهري.

اختبار حاسم:

1. سجّل حالة runtime maintenance.
2. فعّل `maintenance_mode` من شاشة Hub الحالية.
3. نفّذ API عميل عادي.
4. هل يعيد 503 `MAINTENANCE`؟
5. افحص قيمة `ops_config`.
6. أعد الاختبار من AdminOps canonical path.

إذا Hub switch لا يغيّر الـmiddleware:

هذه **Dead Control / False Control** حرجة.

شرط:

`maintenance switches that do not change actual maintenance middleware = 0`

---

# 4. لا تصلح maintenance toggle بربط مصدرين معًا بشكل أعمى

الهدف ليس أن نكتب نفس القيمة في جدولين.

الهدف:

`one maintenance policy source`

إما:
- `ops_config` يصبح المصدر الوحيد،
- أو Settings Registry موحّد يقرأ ويكتب المصدر الرسمي.

احذف/هاجر `business_settings.maintenance_mode` بعد Dry Run إذا أصبح legacy.

# 5. توجد منظومة ثالثة مختلفة للصيانة: Feature Flags

المشروع لديه أيضًا:

`FeatureFlagService`
+
`/admin/maintenance`
+
`RequireFeatureEnabled`

وهذا ليس Global Maintenance نفسه.

افصل رسميًا:

### Global Platform Maintenance

يوقف ميزة بعينها، مع حارس مالي إذا كانت تحتجز أموالًا.

لا تسمّ الاثنين «وضع الصيانة» بشكل يربك المشغل.

# 7. `referral_earning_status` يحتاج إثبات Consumer

# 8. أخطر احتمال: إيقاف «مكافآت الإحالة» لا يوقف الدفع

Registration الحالي يستدعي:

`Helpers::add_refer_commission($request->referral_id)`

عند وجود referral_id.

ومبلغ المكافأة يؤخذ من:

`refer_commission`

لا من:

`referral_earning_status`.

اختبار حاسم:

1. ضع `referral_earning_status = 0`.
2. ضع `refer_commission > 0`.
3. سجّل مستخدمًا جديدًا بـreferral_id صالح.
4. افحص Wallet/Transactions/Ledger.

إذا دُفعت المكافأة:
فالـSwitch الحالي **كاذب ماليًا**.

شرط:

`referral disabled in UI while payouts still occur = 0`

# 9. لا تفعّل Referral Program قبل Financial Truth

إذا برنامج الإحالة مطلوب فعليًا، أنشئ:

`ReferralPolicyService`

- enabled
- reward amount/currency
- eligible inviter
- eligible invitee
- trigger event
- max rewards/day/month
- program budget
- fraud limits
- KYC requirement
- duplicate/device risk
- idempotency
- accounting source
- audit
- reporting

# 10. مكافأة الإحالة لا تُدفع فور إنشاء حساب غير موثق

Registration يجعل الحساب:

`is_kyc_verified = 0`

ثم قد يستدعي عمولة الإحالة فورًا.

هذا يسمح نظريًا بـReferral Farming عبر حسابات وهمية.

غيّر trigger إلى حدث مؤهل موثق، مثل:

`KYC approved + first qualifying activity`

أو policy رسمية أخرى.

لا تدفع لمجرد نجاح POST registration.

شرط:

`referral payouts for unverified throwaway accounts = 0`

---

# 11. Attack Chain يجب اختباره

اختبر هذا السيناريو كحزمة واحدة:

1. Admin يعطل `phone_verification`.
2. Referral amount > 0.
3. `referral_earning_status` ظاهر OFF لكنه غير مستهلك.
4. مهاجم ينشئ عدة حسابات بلا إثبات رقم.
5. كلها تستخدم نفس Referral ID.
6. راقب خروج أموال المكافآت.

هذا اختبار P0.

شرط:

`OTP-off + referral-farming account creation = blocked`

---

# 12. `Helpers::add_refer_commission` يستخدم Legacy Money Path

ابحث هل Referral payout يمر عبر:

- `MoneyService`
- double-entry ledger
- idempotency
- Fee/Policy
- transaction trace

إذا يستخدم فقط `make_transaction()` القديم:

لا تسمح ببرنامج إحالة مالي حي خارج Financial Truth.

أريد:

`referral payouts outside authoritative money service = 0`

---

# 13. مصدر تمويل الإحالة

`add_refer_commission` يختار Admin عبر:

`get_admin_id()`

ثم يدفع من هذا الحساب إلى المُحيل.

هذا ليس Treasury Model احترافيًا.

أثبت:
- أي Admin؟
- لماذا أول Admin؟
- ماذا لو تغير ترتيب الحسابات؟
- ماذا لو رصيده غير كافٍ؟
- هل هو Wallet بشري أم Treasury؟

أنشئ مصدر تمويل رسمي:

`Referral Treasury / Program Liability Account`

لا Wallet موظف.

شرط:

`referral rewards funded from arbitrary first-admin wallet = 0`

---

# 14. `get_admin_id() ?? 1`

أي fallback إلى User ID 1 في حركة مالية أو Attribution يجب أن يختفي.

لا تفترض أن ID 1 Treasury.

شرط:

`financial operations using fabricated/default admin id 1 = 0`

## MAINTENANCE
Global مقابل Per-Feature ومصدر الحقيقة.

## FEATURE FLAGS
الحارس المالي والـcache والـroute parity.

## RBAC
من يرى ومن يعدل ومن يعتمد.

## AUDIT & VERSIONING
before/after/reason/version/rollback.

## CLIENT / FLUTTER
كيف يتزامن التطبيق مع السياسة الفعلية.

## UI & MOBILE
مركز الإعدادات الجديد والنوافذ والـresponsive.

## ATTACK TESTS
خصوصًا OTP-OFF + Referral Farming.

## TESTS
كل الحراس والـregression.

## MIGRATION
كيف أغلقت المفاتيح القديمة دون تغيير إنتاج غير مقصود.

## PRODUCTION TRUTH
commit + DB sources + effective runtime.

أي شيء لم يثبت.
