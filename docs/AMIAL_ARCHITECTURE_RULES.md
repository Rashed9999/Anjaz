# قواعد البنية والتغيير في أميال

هذه خلاصة عملية للتعليمات القائمة في `01_backend/CLAUDE.md` ومهارات المشروع، وليست بديلاً عنها أو تفويضاً لتجاوز بوابة محمية.

## قواعد التغيير

1. قبل تغيير ملف: عيّن مستهلكيه، العقود التي يقدّمها، حواجزه، أثره المباشر وغير المباشر، ودليل التحقق. وثّق الجذر لا العَرَض وحده.
2. لا استبدال جماعي للمعمارية أثناء إصلاح عطل. احتفظ بخدمات Laravel وبنية GetX والـrepositories القائمة في Flutter؛ لا تنشئ محرك صلاحيات أو طبقة مالية موازية.
3. الخادم هو سلطة المصادقة والملكية والصلاحيات والباقات والحدود. إخفاء الزر ليس حارساً، وإظهار الزر لا يمنح الإذن.
4. المالك والموظف وجهاز POS كيانات مختلفة. رمز تفعيل جهاز ليس حساباً ولا وردية ولا مقعداً مفعلاً بعد. جميع الاستعلامات التجارية مقيّدة بالمنشأة.
5. النشاط والباقة محوران منفصلان. لا تعرض خدمة قطاع آخر كوعد ترقية، ولا تخترع مفتاح capability غير مسجل لربط شاشة عامة.
6. كل API جديد يربط consumer ← route ← middleware ← controller ← الخدمة/النموذج القائم. المسار المسجل من ServiceProvider مسار حقيقي؛ افحصه قبل إضافة نسخة أخرى.
7. احفظ عقد الرد القائم: `success`, `code`, `message`, `errors`, `meta`. لا تعتبر 200 أو وجود Map وحده نجاحاً. تحقق من حقول تأكيد الإجراء قبل عرض النجاح.
8. حالات الواجهة مستقلة: تحميل، بيانات، فراغ حقيقي، رفض باقة 402، رفض صلاحية 403، فشل اتصال/خادم. لا تحوّل الخطأ إلى صفر أو قائمة فارغة؛ امنع الإرسال المتزامن ولا تستدعِ setState بعد التخلص من الشاشة.
9. إجمالي النتائج مستقل عن حجم المعاينة/الصفحة. لا تسمِّ الجلسة المفتوحة «جهازاً متصلاً» دون دليل اتصال حي.
10. لا تغير أرصدة أو قيوداً أو تاريخ هجرات استناداً إلى جرد. أي تغيير مالي يستلزم مهارات المجال واختبار المعاملة والعكس والتكرار والتسوية في قاعدة اختبار منفصلة.
11. لا تحذف ملفاً لأنه غير مستورد فقط. افحص المسارات والمزوّدين والتعليقات والتشغيل الديناميكي والتوافق والوظيفة البديلة. ميّز ORPHAN_CANDIDATE عن DEAD وLEGACY_DUPLICATE.
12. لا تسجل الرموز وكلمات المرور وPII في التقارير والفحوص. يعرض حارس السلامة اسم الملف والقاعدة المخالفة فقط.
13. استعادة ملف تالف تكون من آخر نسخة نصية سليمة مع مراجعة ما أضيف بعدها. لا ترجع الفرع كله فتفقد إصلاحات أحدث غير مرتبطة بالعطل.
14. لا تتجاوز رفض أذونات النظام. إذا أذن المالك بالدفع بتحقق ساكن فقط، وثّق ما لم يعمل وما زال يحتاج CI؛ لا تسمِّه نجاحاً كاملاً.

## قواعد سلامة المصدر والفحص

`source-integrity.py` حارس مكمل للمصرّفات: يرفض UTF-8 التالف، محارف التحكم الثنائية، تعارضات الدمج، غياب افتتاح PHP، JSON غير الصالح/مفاتيحه المكررة، وتلف مدخل verify. لا يثبت صحة syntax أو صحة المال.

```bash
python3 -B 01_backend/scripts/source-integrity.py
python3 -B -m unittest discover -s 01_backend/scripts/tests -p 'test_*.py'
bash -n 01_backend/scripts/verify.sh
git diff --check
```

في بيئة اختبار مجهزة، أكمل بالتحقق الفعلي؛ الأوامر التالية ليست منفذة في جلسة الإصلاح:

```bash
# داخل 01_backend وعلى قاعدة اختبار منفصلة
php -l routes/api/amial.php
php -l app/Http/Controllers/Api/V1/Amial/MerchantOperationsCenterController.php
php artisan route:list --path=api/v1/amial/merchant/operations-center
php artisan test --filter=MerchantOperationsCenterTest

# داخل 02_flutter_app
flutter analyze
flutter test test/services_catalog_contract_test.dart test/merchant_adaptive_navigation_test.dart
```

ثم اختبار يدوي للمركز بحساب مالك وعميل وموظف، وخطة بدون فروع وأخرى تسمح بها، وخادم يعيد 402/403/500، وإنشاء دور وموظف وتفعيل جهاز وفتح وردية في بيئة اختبار. يمنع إجراء ذلك على أموال أو عملاء الإنتاج.

## قواعد الالتزام والنشر

- اذكر سبب التغيير في تعليق موضعي عندما يشرح قيداً غير بديهي، وفي سجل التدقيق لكل ملف، وفي رسالة الالتزام.
- قارن tip الفرع البعيد بخط الأساس قبل الدفع. ادفع fast-forward فقط؛ لا force ولا إسقاط لتعديلات متزامنة.
- الفرع الذي يطلق نشر الويب في CI الحالي هو `claude/project-code-review-yjagv`. لا تستبدله باسم مختصر مفترض.
- لا تعطل بوابات structural/backend/docker، ولا تحوّل APK من بناء يدوي إلى بناء تلقائي.
- نداء خطاف Coolify قبول طلب نشر فقط؛ ليس إثبات أن النسخة تعمل. لا يُعلن نجاح النشر قبل دليل مستقل على وصول النسخة وسلامتها.
- يحفظ التقرير حدود الفحوص؛ لا تُحوّل الحالة pending إلى passed عند غياب أداة التشغيل.
