# عقود أميال العابرة للمنصات

## قبل التعديل

1. اذكر المنتجين والمستهلكين ومالك الحقيقة والبيانات الحساسة.
2. ثبّت نسخة العقد الحالية والأثر على التطبيقات والخدمات والطوابير.
3. عرّف معرف ارتباط ثابتًا، و`Idempotency-Key` للطلبات ذات الأثر، ونسخة صريحة للعقد.
4. قرر التوافق: إضافة اختيارية، قراءة مزدوجة، تحويل مضبوط، أو إصدار جديد؛ لا تكسر عميلًا قائمًا بصمت.

## حد أدنى لكل طلب داخلي

- معرّف طلب ومعرّف ارتباط.
- طابع زمني وحد انحراف ساعة.
- توقيع للخدمة المرسلة، وتحقق ثابت الزمن لدى المستقبِل.
- تعريف جهة الطلب وصلاحيتها وحالتها.
- حمولة موثقة وحدود حجم ومخطط تحقق.
- استجابة حتمية تفرق بين القبول، التكرار، الرفض، الفشل المؤقت، والفشل النهائي.

## النشر الآمن

1. انشر المستقبِل المتوافق أولًا.
2. فعّل المرسل بمفتاح ميزة أو نسبة صغيرة حيث ينطبق.
3. راقب مؤشرات القبول والتكرار والرفض والزمن والفشل.
4. احتفظ بمسار رجوع لا يكرر الأثر المالي ولا يفقد الرسائل.
5. احذف التوافق القديم بعد قياس الاستخدام وخطة ترحيل موثقة فقط.

## الاختبارات

اختبر التوقيع الخطأ، إعادة الإرسال، الطابع المنتهي، نسخة قديمة، نسخة جديدة، مهلة الشبكة، استجابة مكررة، وفشل أحد الطرفين. لا يكفي mock داخل مستودع واحد لعقد بين منصتين.

## دليل الاكتمال

لا يوجد دمج قبل وجود اختبار عقد في كل طرف، ونتيجة رحلة تكامل، وخطة رجوع، ومالك واضح للإنذار التشغيلي.
